# 自动预报：保存参数后直接使用

“洪水预报”分为手动预报、自动预报和历史回算，不需要审核或发布参数。

- **手动预报**：选择已保存参数、预报降雨、起报时刻和预见期，点击“开始预报”，只计算一次，不创建自动任务。
- **自动预报**：设置首次起报、间隔（默认1小时）和预见期后点击“自动开始”；点击“关闭自动预报”停止。设置未变时再次开始接续同一条实测状态与起报记录，不重建序列或重复已完成起报。
- **补做预报**：关闭状态下点击，按原参数、降雨来源和资料设置，从下一次未完成起报补到点击时的后台当前整点。上界固定，补完自动关闭；后台重启也不延长该批次。缺少对应历史预报降雨时等待，绝不使用未来实测替代。
- **历史回算**：明确使用历史实测驱动的原有回算，不与当时真正的预报混为一谈。

主页面只常显必要设置、操作、最近/下一次起报与过程图。产品说明、导入格式和成果整理默认折叠。待补次数使用后台时间，不取决于浏览器时钟。

- 参数应用于南安溪当前1 km全流域模型，出口过程显示徐畈断面；可查看网格状态与河道流量。
- 例如间隔1小时、预见期24小时，表示每小时重新计算未来24小时，不是每小时重新率定。
- 第一次按所选参数的预热/初态设置形成实测状态；随后只用新实测降雨推进该状态，再从起报时刻分支计算预报。
- 预报分支末状态不会回写实测状态。不自动更换参数；更换参数需停止后重新启动，重新形成初态。
- 调度由本地后台持久运行，关闭浏览器页面不停止。后台必须保持启动；服务重启后承接已完成状态、重试被中断计算，不将中断计算认定为成功。
- 没有覆盖预见期的降雨产品、实测缺测时等待并显示原因，资料补齐后重试。不补零、不缩短预热、不使用未来实测冒充降雨预报。
- 各次计算默认临时，可按需保存成果；保存参数与保存成果分开。历史回算入口保留。

## 降雨产品

当前没有配置气象供应商实时接口。可以在页面导入JSON，也可以让现有数据程序持续向同源本地接口 `POST /api/model/forecast-rain` 登记新产品。后台自动选择指定来源中，产品起报时刻不晚于本次起报且覆盖完整预见期的最新版本。

时间均为北京时间、本地整点，不带时区后缀。`hour-ending`表示第一项雨量覆盖产品起报后的第一个小时，标记在该小时末。单位为该小时累计毫米，不是累计到当前时刻的总雨量。不要把供应商累计量直接导入。

均匀雨量示例（仅说明格式，不是真实预报）：

```json
{
  "name": "降雨产品示例",
  "contextKey": "nananxi-xufan:distributed-xinanjiang:nananxi-xufan-1km",
  "sourceId": "weather-product",
  "sourceLabel": "实际气象产品名称 · 全域均匀处理",
  "issueTime": "2026-10-19T12:00:00",
  "unit": "mm",
  "timeConvention": "hour-ending",
  "hourlyRainfallMm": [0, 1.2, 3.5, 0]
}
```

逐网格产品将 `hourlyRainfallMm` 替换为 `gridIds` 和 `hourlyGridRainfallMm`：每行为一个小时，每列对应一个网格。编号必须完整匹配当前模型，可调整顺序，服务端按编号映射；不接受缺格、重复编号或静默空间插值。产品预见期沿用现有模型的1–72小时契约，请在导入前完成单位、时区、累计差分和模型网格重映射。

同一来源保持同一个 `sourceId`，更新产品的 `issueTime` 与雨量即可。若没有新批次，但已有批次仍覆盖完整预见期，则按真实有效时刻截取；不会将旧产品整体平移。旧人工情景版本仍可按原起报时刻查看和计算。

调度接口：`GET/POST /api/model/automatic-forecasts`、`GET /api/model/automatic-forecasts/{id}`、`POST .../{id}/start`、`POST .../{id}/stop`、`POST .../{id}/catch-up`、`GET .../{id}/issues`。控制请求体均为 `{}`。列表同时返回 `currentTime`（北京时间）。同一流域同时只启动一套自动或补做序列，避免多套设置混用。手动预报复用 `POST /api/model/operations`，操作标识 `manualForecast`；降雨版本、参数、起报时刻和预见期均冻结到执行记录中。
