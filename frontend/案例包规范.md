# 新安江水文模型案例清单与静态资源规范

本文约定前端案例目录中的 `catalog.json`、`manifest.json` 和轻量静态资源。它们负责案例选择、展示元数据和浏览器资源定位；数值任务、运行输入及结果由 Python 后端和所选工作区管理，接口契约见[API 文档](../backend/API.md)。

## 1. 设计目标

每个流域案例都应当是一个可独立复制、校验和迁移的目录。案例之间并行存在，不能因为切换案例而共用另一案例的空间资料、参数、状态草稿或样例结果。

统一案例包需要满足：

- 使用稳定的英文 `id` 作为目录名和上下文标识；
- 使用相同的清单层级，差异通过能力和状态字段表达；
- `1km`、`0p1deg` 等模型尺度在同一案例内并列保存；
- 浏览器只读取轻量预览和目录，原始 MDB、Excel、NetCDF、栅格和大型结果留在外部资料区；
- 资源引用不绑定某台电脑的盘符、用户目录或网站根目录；
- 案例资料状态、页面能力和后端运行就绪度分别记录，不用静态预览或 fixture 冒充数值成果。

## 2. 目标目录结构

目标结构如下：

```text
frontend/public/data/
├─ projects/
│  ├─ catalog.json
│  └─ <case-id>/
│     ├─ manifest.json
│     ├─ spatial/
│     │  ├─ metadata.json
│     │  ├─ basin.geojson
│     │  ├─ rivers.geojson
│     │  ├─ stations.geojson
│     │  ├─ sections.geojson
│     │  └─ ...
│     ├─ observations/
│     │  ├─ catalog.json
│     │  ├─ flood-events.json
│     │  └─ previews/
│     ├─ forcing/
│     ├─ parameters/
│     ├─ 1km/
│     │  ├─ spatial.json
│     │  ├─ datasets.json
│     │  └─ fixtures.json
│     └─ 0p1deg/
│        ├─ spatial.json
│        ├─ datasets.json
│        └─ fixtures.json
└─ ...
```

### 当前兼容情况

- 南安溪-徐畈和里龙普曲已基本使用 `projects/<case-id>/...` 目录。
- 色林错资源目前仍位于 `public/data/selinco`，由项目服务映射到案例上下文。
- `src/data/domainContext.js` 仅保留三个已有案例的离线启动兜底；`projectCatalogService.js` 启动时读取总目录和案例清单，再登记案例，不要求为新案例添加源码常量。
- 有目录但未写入 `catalog.json` 的案例不会自动被扫描。静态前端无法枚举服务器文件夹；登记一条清单记录才是扩展入口。

## 3. 总目录 `catalog.json`

文件位置：`public/data/projects/catalog.json`。

它只负责列出案例，不承载具体资料。建议字段：

```json
{
  "schemaVersion": "1.0",
  "updatedAt": "2026-10-08",
  "modelFramework": {
    "id": "distributed-xinanjiang",
    "name": "分布式新安江模型"
  },
  "projects": [
    {
      "id": "nananxi-xufan",
      "name": "南安溪-徐畈",
      "status": "partial",
      "statusLabel": "前端资料部分可用",
      "manifest": "./nananxi-xufan/manifest.json"
    }
  ]
}
```

约束：

- `id` 全局唯一，只使用小写字母、数字和短横线；
- `manifest` 指向案例包内文件，优先使用相对路径；
- 目录中没有可展示资料时也可以登记，但必须填 `status` 和 `statusLabel`；
- `catalog.json` 不直接列出每个数据文件，数据文件由案例的 manifest 和分辨率目录管理。

## 4. 案例 `manifest.json`

文件位置：`public/data/projects/<case-id>/manifest.json`。

建议的顶层字段：

| 字段 | 含义 |
| --- | --- |
| `schemaVersion` | 清单格式版本 |
| `id` | 与目录名、catalog 中的案例 ID 一致 |
| `name` | 页面展示名称 |
| `basinType` | 流域/湖泊类型 |
| `modelFrameworkId` | 使用的模型框架，如 `distributed-xinanjiang` |
| `source` | 原始资料来源、来源类型和备注 |
| `capabilities` | 案例登记的业务能力；资料覆盖和后端运行状态另行核验 |
| `resolutions` | 各模型尺度的配置和资料状态 |

`capabilities` 表示案例目录登记的业务能力，不单独证明当前工作区已有相应输入或已生成数值成果；实际计算还须由后端校验任务条件和资料。

每个分辨率至少应有：

```json
{
  "label": "1 km",
  "status": "partial",
  "statusLabel": "实测资料已接入",
  "spatialStatus": "source-verified",
  "inputStatus": "observed-data-ready",
  "spatialManifest": "./1km/spatial.json",
  "datasetCatalog": "./1km/datasets.json",
  "fixtureCatalog": "./1km/fixtures.json"
}
```

当前文件使用 `spatialManifest`、`datasetCatalog` 和 `fixtureCatalog` 等字段；后续可以在不改变含义的前提下统一为 `paths` 对象，但不能让同一个字段在不同案例中表示不同内容。

## 5. 状态字段

### 5.1 案例或分辨率 `status`

建议使用以下有限集合：

| 值 | 含义 |
| --- | --- |
| `draft` | 目录已创建，资料和清单仍在准备 |
| `spatial-only` | 只有边界、河网、站点、地形等空间资料 |
| `partial` | 有部分真实观测或输入资料，但尚不能代表完整运行方案 |
| `frontend-fixture` | 前端使用样例/试算数据，不能视为正式模型成果 |
| `ready-for-backend` | 案例静态目录和输入清单已整理，仍需独立核验后端适配、资料覆盖和生产资格 |

### 5.2 资料状态

- `spatialStatus`：`missing`、`source-verified`、`available`、`source-verified-preview-pending`。
- `inputStatus`：`missing`、`partial-real`、`observed-data-ready`、`fixture-only`。
- `resultSource`：`unavailable`、`frontend-fixture`、`external-service`。

如果资料缺少，使用 `missingInputs` 明确列出缺失项，例如小时降水、出口流量、气温、蒸发或初始状态。不要用“已接入”“可运行”等文字掩盖缺口。

## 6. 资源路径规则

### 6.1 浏览器静态资源

- 新增清单使用相对于清单或项目根目录的路径，例如 `./spatial/basin.geojson`、`./1km/datasets.json`。
- 不写 `F:\...`、`C:\...`、用户目录或其他机器专属路径。
- 不把 `/data/...` 当成最终规范；它是历史网站根路径写法，部署到 `/platform/` 等子目录时可能失效。
- 前端统一通过 URL 解析函数结合 `import.meta.env.BASE_URL` 生成实际请求地址。

### 6.2 外部模型资料

NetCDF、原始 Excel、MDB、栅格和大型结果可以在清单中登记 `filePattern`、`source`、版本和时间范围，但这些字段只是资料血缘，不表示浏览器会直接读取本机文件。

### 6.3 后端地址

后端 API 地址由统一平台配置。生产网页通过同源 `/api/model` 调用服务；本地 Vite 开发服务器将该路径代理到 `127.0.0.1:8878`。案例静态资源路径与工作区数据库、模型输入和任务成果相互独立。

资料就绪与 `capabilities` 分开判断。缺少资料或模型适配的案例可以浏览静态空间资料，但不能借用其他案例的参数、状态或结果。

## 7. 新增案例流程

### 当前新增案例流程

1. 为案例确定稳定的 `<case-id>`，建立 `public/data/projects/<case-id>/` 目录。
2. 创建 `manifest.json`，至少登记名称、来源、能力、状态和分辨率。
3. 按需创建 `spatial`、`observations`、`forcing`、`parameters`、`1km`、`0p1deg` 等目录，只放轻量前端资料或目录文件。
4. 在 `catalog.json` 增加一条案例记录。
5. 重新加载页面。`projectCatalogService.js` 会读取该清单，生成独立的流域/尺度上下文；常规案例无需修改 `domainContext.js`。新的业务形态若超出现有通用页面能力，另行增加展示适配，不复制现有案例数据充当兜底。
6. 运行 `npm test`、`npm run build:unified`，并手动切换已有案例确认上下文没有串用。
7. 在文档中记录资料缺口、路径迁移情况和 `status`，再提交到版本控制。

### 后续平台内“新建案例”

案例登记由清单驱动。页面不直接创建目录或写入本机文件；新增案例应按同一结构提交清单和轻量资源，业务资料、浏览器草稿和模型执行就绪状态分别维护。

### 路径维护与校验

在 `frontend` 目录运行：

```bash
node scripts/normalize_json_resource_paths.mjs
```

默认只检查 `public/data` 中遗留的 `/data/...` JSON 引用，不写文件。确认输出后，添加 `--write` 才执行路径规范化。新写入的路径相对于声明它的 JSON 文件；`resourceUrl.js` 和 `projectResourceService.js` 负责最终解析。名称、ID、状态、日期和来源说明不是资源路径，不参与 URL 拼接。

## 8. 验收清单

- [ ] 案例 ID、目录名、catalog 和 manifest 一致。
- [ ] 所有资源引用不含盘符、用户目录和未解析的网站根路径。
- [ ] 缺失资料写入 `missingInputs`，没有虚构运行结果。
- [ ] 不同案例、不同尺度的状态、参数、资料和 fixtures 可以独立切换。
- [ ] 资料或模型能力未就绪时，页面明确显示状态，不伪造计算成果。
- [ ] `npm test` 和 `npm run build:unified` 通过。
- [ ] 文档、脚本和清单与案例目录一起进入 Git；大型原始资料另行版本化。
