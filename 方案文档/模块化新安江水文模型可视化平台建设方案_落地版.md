# 高寒区新安江水文模型业务化预报与可视化平台建设方案（落地版）

## PostgreSQL + PostGIS + NetCDF + Python + Vue 3 一期技术蓝图

编制日期：2026 年 7 月

---

## 一、文档定位与一期边界

本方案用于指导高寒区新安江水文模型从资料接入、预处理、连续运行到预报研判的第一期建设。它不是单纯的界面原型，也不是一次性科研脚本的说明书，而是后续可以持续增加高寒区水文过程、站网资料和模型方案的业务底座。

一期的目标不是一次完成所有模型功能，而是在一个试点流域上建立完整、可复算的闭环：原始资料可追溯，入模资料有版本，状态能够继承，预报结果可以回查，页面能够解释一次预报为何得到该结果。

| 范围 | 一期必须交付 | 一期暂不纳入 |
|---|---|---|
| 空间范围 | 一个试点流域、子流域、河网、站点和一个或多个控制断面 | 多流域统一运营、跨区域数据交换平台 |
| 数据 | 降水、气温、蒸散发或蒸散发替代量、水位或流量、预报降水 | 全量遥感反演链、所有历史资料自动清洗 |
| 模型 | 新安江核心、降雨降雪相态、度日融雪、冻土下渗修正、河网汇流 | 能量平衡融雪、复杂同化、多模型自动集成 |
| 运行 | 实时预报、历史回算、状态重建、运行档案 | 高并发集群调度、跨单位工作流编排 |
| 前端 | 实时监视、预报作业、状态诊断、运行档案、基础配置 | 三维展示优先、移动端、演示型大屏 |

一期必须坚持以下四条底线。

1. 前端不直接读写 NetCDF 文件路径，也不直接拼装模型输入。
2. 每次模型运行都生成唯一 `run_id`，并固定引用的数据、参数、状态和程序版本。
3. 原始观测、质量控制结果、入模产品和模型成果分别保存，任何一步都不能覆盖上一步。
4. 高寒区过程以可插拔模型模块接入，不能把降雪或冻土逻辑散落在页面、脚本和数据库触发器中。

## 二、总体架构与技术选型

### 2.1 推荐架构

第一期采用“单体业务平台 + 独立计算进程”的架构，而不是一开始拆成多个微服务。模型计算、NetCDF 读写和资料预处理本来就以 Python 为主，因此 API 服务与计算 Worker 共享同一套 Python 领域代码；二者进程独立，职责清晰，后期可以按负载再拆分。

```text
站网资料 / 格点资料 / 预报降水
                |
                v
原始资料入库 -> 质量控制与空间归集 -> 入模 NetCDF 产品
       |                    |                    |
       v                    v                    v
 PostgreSQL/PostGIS <--- 产品目录与版本登记 ---> NC 文件库
       |                                         |
       |                                         v
       +---- 运行编排 API -> 计算 Worker -> 状态 / 结果 NetCDF
                                      |
                                      v
                          运行档案、指标、事件日志
                                      |
                                      v
                     Vue 作业台：地图、过程线、表格、诊断
```

该结构中，PostgreSQL 是业务事实和索引的唯一来源，NetCDF 是多维数值产品的唯一载体。运行时先由数据库确定“本次应该使用哪一个产品和版本”，再由 Worker 打开对应 NetCDF 文件；运行结束后，Worker 把产物登记回数据库。这样既不把大矩阵硬塞进关系表，也不会让 NC 文件游离于业务档案之外。

### 2.2 一期技术栈

| 层次 | 一期选择 | 选择理由 |
|---|---|---|
| 数据库 | PostgreSQL 16 + PostGIS 3 | 同时满足站网时序、空间对象、事务、版本和空间查询 |
| 数值文件 | NetCDF4，Python xarray + netCDF4 | 适合 `time`、`subbasin`、`section`、`y`、`x` 等多维水文产品 |
| 后端 API | Python 3.11 + FastAPI + Pydantic + SQLAlchemy 2 + Alembic | 与模型、xarray 和科学计算代码同语言，接口文档可自动生成 |
| 计算 Worker | Python 独立进程，复用模型核心包 | 将长时计算与 HTTP 请求隔离，避免网页请求被模型运行阻塞 |
| 前端 | Vue 3 + TypeScript + Vite + Vue Router + Pinia | 新项目采用当前维护路径，组件、类型与工程化能力更稳定 |
| 业务组件 | Element Plus + ECharts | 分别负责表单表格和过程线、雨量图、指标图 |
| 二维地图 | OpenLayers | 满足站点、河网、子流域、GeoJSON 和栅格叠加，不强制引入三维场景 |
| 部署 | Docker Compose + Nginx 或 Caddy | 本地和服务器使用同一服务边界，便于迁移与备份 |
| 测试 | pytest、PostgreSQL 集成测试、Playwright | 同时验证模型、数据产品、接口和关键作业流程 |

Redis、Celery、消息队列、GeoServer 和 Kubernetes 均不作为一期前置依赖。只有在出现以下明确条件后再引入：同一时刻需要多个长任务排队、WebSocket 广播跨多个 API 进程、空间图层无法由普通 GeoJSON 或切片服务支撑，或部署已经扩展到多台机器。

### 2.3 不照搬三峡项目的部分

三峡开源项目的价值主要在信息呈现和交互组织，不在基础数据与模型生产化。它使用 Vue 2、Cesium、Spring Boot、FastAPI、MySQL、Redis 等多套服务，并包含本地模拟站点数据降级逻辑；这些选择适合学习型三维沙盘，但会增加本项目第一期的维护成本。

| 可借鉴 | 本项目的落地方式 | 不直接照搬 |
|---|---|---|
| 左导航、业务面板、地图和过程线联动 | 一图、一线、两侧栏的二维预报作业台 | Cesium 三维场景作为一期核心 |
| HTTP 查询、WebSocket 实时推送、SSE 任务进度 | HTTP 负责查询和命令，WebSocket 负责监测事件，SSE 负责单次运行进度 | 多个后端网关和前端直连内部服务 |
| 图表、预警、运行进度、站点飞行定位等交互形态 | 用 ECharts、OpenLayers 和组件化面板实现 | 数千行的综合面板组件和事件总线式耦合 |
| 分区汇流和拓扑展示 | 将河网拓扑、子流域关系放入 PostGIS 和模型配置 | 用演示数据替代资料质控与版本管理 |

### 2.4 后续扩展边界

一期虽然采用单体部署，但接口和目录必须保留拆分边界。API 只负责鉴权、校验、查询和创建运行任务；Worker 只负责预处理、模型计算和产品写入；模型核心不依赖数据库会话、HTTP 框架或前端字段。这样以后替换调度器、增加多 Worker 或接入新的模型过程时，不需要重写已有业务逻辑。

## 三、数据分层、数据库与 NetCDF 协同

### 3.1 数据分层原则

数据必须按“原始资料、采用资料、入模产品、状态产品、结果产品、运行档案”分层。原始资料用于保真和追溯，采用资料用于业务判断，NetCDF 用于模型读取和数值分析，数据库用于对象关系、版本、索引和审计。

| 数据类别 | 主存储位置 | 典型内容 | 说明 |
|---|---|---|---|
| 基础空间对象 | PostgreSQL/PostGIS | 流域、子流域、河段、断面、站点、拓扑 | 稳定对象和空间关系，修改必须版本化 |
| 原始观测 | PostgreSQL | 原值、观测时间、接收时间、来源、批次 | 只追加，不在原记录上直接改值 |
| 质量控制与采用值 | PostgreSQL | QC 标志、订正值、采用值、订正原因 | 通过视图或明确版本选择给预处理使用 |
| 格点与子流域驱动 | NetCDF | 降水、温度、蒸散发、质量标志 | 数据库保存产品目录和元数据 |
| 模型状态 | NetCDF | 张力水、自由水、汇流蓄量、积雪、冻土状态 | 状态快照可继承、可回算 |
| 模型结果 | NetCDF + PostgreSQL 摘要 | 子流域产流、断面过程线、指标 | 大序列进 NC，洪峰等摘要入数据库 |
| 运行档案 | PostgreSQL | `run_id`、依赖版本、状态、日志、产品引用 | 预报、回算、率定均使用同一档案机制 |

### 3.2 PostgreSQL 逻辑模式

建议按业务职责划分 schema，而不是把全部表堆在 `public` 下。以下为一期最小表集合；字段可以细化，但表的职责不要混淆。

| Schema | 核心表 | 主要职责 |
|---|---|---|
| `ref` | `basin`、`subbasin`、`reach`、`section`、`station` | 管理稳定水文对象、编码和 PostGIS 几何 |
| `obs` | `observation_raw`、`observation_selected`、`qc_event` | 保留原始值、采用值和质量控制依据 |
| `catalog` | `data_product`、`data_asset`、`product_variable` | 登记每个 NetCDF 或原始文件的路径、校验码、时空范围和变量 |
| `model` | `model_profile`、`parameter_set`、`state_snapshot` | 管理模型能力组合、参数版本和状态快照 |
| `ops` | `model_run`、`run_input`、`run_output`、`run_event` | 管理运行请求、输入清单、成果引用、进度和错误 |
| `audit` | `operation_log` | 记录人工订正、手工状态修正、配置变更和发布动作 |

关键约束如下。

1. 所有水文对象使用稳定业务编码，同时使用数据库主键；接口优先暴露业务编码，内部关联使用主键。
2. `observation_raw` 的唯一性至少由 `station_id`、`variable_code`、`observed_at`、`source_batch_id` 约束，允许同一时刻多来源并存。
3. `observation_selected` 必须能反查原始记录、质量规则和人工订正依据，不能只留下最终数值。
4. `data_asset` 必须保存相对路径、SHA-256 校验码、文件大小、时间范围、空间范围、生产程序版本和产品版本。
5. `model_run` 不能只记录“成功或失败”，还必须固定 `model_profile_id`、`parameter_set_id`、`state_in_id`、运行窗口、预见期和代码版本。
6. 站点时序表至少建立 `(station_id, observed_at)` 索引，空间表建立 GiST 几何索引，产品目录以产品类型、流域、时间范围和版本建立复合索引。

### 3.3 NetCDF 产品规范

NetCDF 文件不是临时中间文件，而是受版本控制的数据产品。第一期统一采用 UTC 时间、明确单位、明确缺测值和明确 `product_schema_version`。变量命名优先使用可读英文名，说明文字和单位写入属性，不在文件名中拼接隐含语义。

| 产品 | 推荐维度 | 最小变量 | 关键全局属性 |
|---|---|---|---|
| `forcing.nc` | `time, subbasin`，必要时 `time, y, x` | `precipitation`、`air_temperature`、`potential_evaporation`、`quality_flag` | `basin_code`、`data_version`、`source_product_ids` |
| `state_in.nc` / `state_out.nc` | `subbasin, state_variable` | `wu`、`wl`、`wd`、`free_water`、`routing_storage`，以及启用的雪冻土状态 | `valid_at`、`state_version`、`parent_state_id` |
| `result.nc` | `time, section` 和 `time, subbasin` | `discharge_forecast`、`runoff_total`、`runoff_surface`、`runoff_interflow`、`runoff_groundwater` | `run_id`、`parameter_version`、`state_in_id` |
| `diagnostic.nc` | 按需使用 `time, subbasin` | 面雨量、产流面积、融雪补给、冻土修正量、质量统计 | `run_id`、`diagnostic_version` |

每个产品必须至少包含 `time` 坐标及其单位、变量单位、缺测值、生成时间、生产程序 Git 提交号或发布版本、上游产品 ID 列表和 SHA-256。对于内部产品，可以在 CF Convention 的基本时间与坐标规范上增加项目属性；不要为了“符合格式”而在第一期引入难以维护的自定义标准。

### 3.4 文件目录与产品登记

文件路径使用相对根目录，数据库中不存用户电脑的绝对路径。实际根目录通过环境变量 `DATA_ROOT` 配置，开发机、服务器和测试环境可以映射到不同位置。

```text
data-products/
  raw/
    station/{source}/{yyyy}/{mm}/
    grid/{source}/{yyyy}/{mm}/
  curated/
    forcing/{basin_code}/{product_version}/forcing.nc
  state/
    {model_profile}/{state_version}/state.nc
  result/
    {run_id}/result.nc
  diagnostic/
    {run_id}/diagnostic.nc
  archive/
    manifests/{run_id}.json
```

前端永远只获得产品 ID、下载授权地址或已经聚合的 JSON 结果；它不持有服务器文件路径。运行清单 `archive/manifests/{run_id}.json` 与数据库 `ops.model_run` 互相校验，可在数据库恢复或文件迁移后重新建立索引。

## 四、模型模块、状态继承与连续预报

### 4.1 高寒区模型能力组合

高寒区版本不应把“新安江模型”简单等同于单一产流公式。推荐将模型能力组织为 `model_profile`，每个 profile 明确启用哪些模块、参数集合和状态变量。第一期选择一个可解释、可率定的最小组合，之后再增加复杂过程。

```text
forcing
  -> precipitation phase partition
  -> degree-day snowmelt
  -> frozen-soil infiltration adjustment
  -> Xinanjiang evapotranspiration and runoff generation
  -> runoff source partition
  -> subbasin routing
  -> river-network routing
  -> section forecast and diagnostics
```

| 模块 | 一期职责 | 输入 | 输出 | 一期边界 |
|---|---|---|---|---|
| 相态判别 | 按温度或湿球温度把降水拆为雨和雪 | 降水、气温、阈值参数 | 雨量、雪量 | 不实现复杂云微物理过程 |
| 融雪模块 | 使用度日法产生融雪补给 | 气温、雪量、积雪水当量 | 融雪量、更新后的 SWE | 不实施能量平衡模型 |
| 冻土修正 | 用冻结指数或有效下渗系数修正下渗和地表产流 | 土壤状态、气温、冻结参数 | 修正量、冻结状态 | 先做可率定的经验结构 |
| 新安江核心 | 蒸散发、蓄满产流、分水源 | 入模水量、蓄水状态、参数 | 各径流分量、更新状态 | 保持纯计算，不读数据库 |
| 汇流模块 | 子流域和河网传播 | 径流分量、河网拓扑、汇流状态 | 出口和断面流量 | 一期优先一种稳定方法 |

模型核心函数只接收结构化 `Forcing`、`State`、`Parameters` 和 `Topology` 对象，只返回 `Result`、`State` 与 `Diagnostics`。数据库读写、NetCDF 打包、HTTP 请求和页面格式化全部在模型核心之外完成。

### 4.2 状态快照与版本链

连续预报的可信度取决于状态管理。每个可用状态快照都要有 `state_version`、`valid_at`、`parent_state_id`、`source_run_id`、`parameter_set_id`、`data_version` 和产品 ID。状态不是普通结果附件，也不允许被新的预测结果静默覆盖。

滚动预报按照以下顺序执行。

1. 找到目标 `model_profile` 和 `t0` 之前最新、已确认的状态快照。
2. 从该状态快照推进到当前时刻，使用已通过质控的实测或采用资料。
3. 生成“现在时刻”的新状态快照，并将其登记为本次运行的 `state_out_id`。
4. 读取当前时刻之后的预报降水、温度和蒸散发产品。
5. 从新状态向未来预见期计算，生成断面预报和诊断产品。
6. 将输入产品、参数、状态、结果、指标和日志固定到同一个 `run_id`。
7. API 发布可查询摘要，前端按 `run_id` 展示而不是读取“最新文件”。

当资料补传、订正或参数切换后，系统不修改旧运行。它创建新的 `model_run`，引用新的输入版本，并从受影响时刻之前最近的有效状态开始重建。旧结果保留，新旧运行可在档案页对比。

### 4.3 运行类型与质量门槛

| 运行类型 | 用途 | 状态来源 | 是否发布业务结果 |
|---|---|---|---|
| `realtime_forecast` | 正式滚动预报 | 最近确认状态，先推至当前时刻 | 是，满足资料质量门槛时发布 |
| `hindcast` | 历史场次复算与验证 | 指定历史状态或预热结果 | 否，进入研究和评价档案 |
| `calibration` | 参数率定与模型比较 | 指定事件与预热窗口 | 否，生成参数候选版本 |
| `state_rebuild` | 补传资料、订正资料后的状态重建 | 受影响时刻前的可用状态 | 由业务人员确认后发布 |

发布前至少检查关键站到报率、关键变量缺测比例、入模产品校验码、状态时间一致性和水量平衡。门槛未满足时，运行可以完成，但状态必须标记为 `degraded` 或 `failed`，前端必须展示原因，不能用随机数或模拟资料静默替代。

## 五、运行编排、API 与实时通信

### 5.1 运行请求与异步任务

模型运行不能在 HTTP 请求生命周期内同步完成。`POST /api/v1/runs` 仅负责校验请求、创建 `model_run` 和返回 `202 Accepted`；Worker 领取运行后持续写入 `run_event`，前端通过 SSE 获取进度。这样即使模型运行十分钟，也不会占住浏览器请求或导致用户重复点击。

| 接口 | 作用 | 主要返回 |
|---|---|---|
| `POST /api/v1/runs` | 创建预报、回算或率定运行 | `run_id`、初始状态、SSE 地址 |
| `GET /api/v1/runs/{run_id}` | 查询运行状态和依赖版本 | 状态、输入清单、指标、错误摘要 |
| `GET /api/v1/runs/{run_id}/series` | 查询断面或子流域过程线 | 时间数组、实测值、预报值、单位 |
| `GET /api/v1/runs/{run_id}/diagnostics` | 查询状态和产汇流诊断 | 状态摘要、贡献量、质量说明 |
| `GET /api/v1/archive/runs` | 条件检索历史运行 | 分页运行列表和版本信息 |
| `GET /api/v1/monitor/stations` | 查询当前或历史站点快照 | 站点值、QC 状态、预警等级 |
| `GET /api/v1/events/runs/{run_id}` | SSE 推送单次长任务进度 | 阶段、百分比、日志摘要、终态 |
| `WS /api/v1/ws/monitor` | 推送实时站网和预警变化 | 站点增量、预警事件、数据质量变化 |

前端创建运行时只传递业务语义，例如目标断面、起报时刻、预见期、模型 profile 和方案 ID。后端负责解析实际的 `parameter_set`、`state_snapshot` 与 `data_product`，并把最终解析结果写入运行清单。

### 5.2 通信边界

HTTP 是业务查询和明确命令的主通道；WebSocket 只用于“最新站点数据、预警和质量状态”等持续变化的监视事件；SSE 只用于一条运行任务的阶段性进度。三种方式不要互相替代，也不要让前端同时维护多条不受控的长连接。

统一事件字段至少包括 `event_id`、`event_type`、`occurred_at`、`basin_code`、`run_id`、`payload_version` 和 `payload`。事件消费者必须能根据 `event_id` 去重，断线重连后通过 HTTP 回补最终状态。

### 5.3 运行事件最小状态机

```text
queued -> validating -> preparing -> running -> writing_products -> completed
                     \-> failed
queued / validating / running -> cancelled
```

每次状态变更必须记录发生时间、执行组件和可读说明。错误日志不能只存在容器标准输出，也要以摘要写入 `ops.run_event`，便于运行档案和问题排查。

## 六、前端作业台与组件边界

### 6.1 页面优先级

页面按水文业务任务拆分，而不是按技术功能堆叠。第一期只实现能够支撑闭环运行的四个页面，率定验证和复杂报表可以在核心链路稳定后加入。

| 页面 | 一期职责 | 核心对象 |
|---|---|---|
| 实时监视 | 查看站网到报、资料质量、降雨和预警 | 站点、河网、子流域 |
| 预报作业台 | 选择断面和方案，发起运行，跟踪进度，查看过程线 | 断面、预报运行、时间轴 |
| 状态与档案 | 查看状态快照、运行版本链、成果和诊断 | `run_id`、`state_version`、参数集 |
| 基础配置 | 管理站点、子流域、断面、阈值和模型 profile | 参考对象与版本 |

### 6.2 预报作业台布局

工作台采用“一图、一线、两侧栏”。中间是二维流域地图；左侧是图层、运行条件和方案选择；右侧根据当前选中对象展示站点、子流域或断面详情；底部是可展开的时间轴和过程线。地图回答“哪里发生了什么”，过程线回答“何时、多少、是否可信”。

时间改变时，地图图层、站点快照、子流域状态和过程线必须使用同一 `as_of` 或 `run_id`，不能各自请求“最新值”。选中表格行可定位站点或断面，勾选图层只改变显示状态，不改变模型数据。

### 6.3 前端目录和组件规则

```text
apps/web/src/
  pages/
    monitoring/
    forecast-workbench/
    run-archive/
    system-config/
  features/
    stations/
    subbasins/
    forecasts/
    states/
    layers/
  components/
    map/
    charts/
    tables/
    run-panel/
    quality-badge/
  services/
    api-client/
    websocket/
    sse/
  stores/
  types/
```

组件只处理一种职责。例如 `StationLayer` 只绘制站点，`BasinStateLayer` 只绘制子流域状态，`HydrographChart` 只绘制过程线，`ForecastRunPanel` 只创建和跟踪运行，`RunArchiveTable` 只查询和筛选档案。地图组件不负责模型调用，图表组件不负责状态编辑，运行按钮不拼接 NC 文件名。

开发环境可以有 Mock 数据，但必须通过显式的 `VITE_DATA_MODE=mock` 开关启用，并在界面明显标识为演示模式。生产模式下接口失败必须展示“数据不可用”和具体来源状态，绝不能自动生成模拟值。

## 七、本地部署、配置与运维

### 7.1 服务组成

第一期部署由以下服务组成。它们可以在一台工作站或服务器上运行，使用 Docker Compose 固定版本和挂载目录。

```text
reverse-proxy
  -> web: Vue 静态文件
  -> api: FastAPI REST、WebSocket、SSE
  -> worker: 预处理、模型运行、NetCDF 写入
  -> postgres: PostgreSQL + PostGIS
  -> data-products volume: NC 产品、清单、原始文件
```

本地研究开发可以只将 PostgreSQL 容器化，API 和 Worker 在 Python 虚拟环境中运行，便于调试模型。部署到业务主机时，Web、API、Worker 和数据库统一由 Compose 管理。无论哪种方式，`DATA_ROOT` 必须映射到稳定的数据磁盘，而不能使用容器临时目录。

### 7.2 配置项

机密信息不提交到 Git。每个环境只保留 `.env.example`，实际密码、令牌和路径通过 `.env` 或部署平台密钥注入。

| 配置项 | 含义 |
|---|---|
| `DATABASE_URL` | PostgreSQL 连接串 |
| `DATA_ROOT` | NC 产品和原始资料的根目录 |
| `MODEL_CODE_VERSION` | 当前模型发布版本或 Git 提交号 |
| `FORECAST_SCHEDULE` | 滚动预报计划，例如每小时或每三小时 |
| `QC_PROFILE` | 当前质量控制规则版本 |
| `APP_TIMEZONE` | 业务显示时区；存储统一采用 UTC |
| `CORS_ORIGINS` | 允许访问 API 的前端地址 |

定时预报由 Windows 任务计划程序、cron 或容器调度触发 API 或命令行入口，不由浏览器定时器触发。任务计划只负责“何时启动”，实际的幂等检查、重试和运行建档仍由 API/Worker 完成。

### 7.3 备份与恢复

每日备份 PostgreSQL，同时备份新增或变更的 NetCDF 产品和运行清单。恢复时先恢复数据库，再根据 `data_asset` 校验文件路径、大小和 SHA-256；若文件缺失，运行档案必须明确标记为不可复现，而不是返回错误的旧结果。

至少每月演练一次“从备份恢复一个历史 `run_id` 并重新读取其结果”的流程。该演练是对“SQL + NC 协同”是否真实可用的最低检验。

## 八、实现里程碑与验收条件

### 8.1 建设顺序

前端不应先于数据合同和模型运行档案单独开工。推荐按以下顺序推进，每个里程碑都需要有可运行样例和验收结果。

| 里程碑 | 交付内容 | 通过条件 |
|---|---|---|
| M0：规则冻结 | 试点流域、时间步长、对象编码、产品清单、版本规则 | 一张对象关系图和一份接口/变量字典经确认 |
| M1：数据底座 | PostGIS 基础对象、观测原始表、QC 规则、产品目录 | 可导入一个历史洪水过程并追溯到原始记录 |
| M2：入模与模型 | `forcing.nc`、模型核心 CLI、状态快照、结果产品 | 一个历史场次可重复运行，水量与时间轴通过检查 |
| M3：运行服务 | FastAPI、Worker、`model_run`、SSE 进度、运行档案 | 创建运行后可查询进度、结果、日志和全部依赖版本 |
| M4：作业台 | 监视、预报、档案三类页面，地图和过程线联动 | 业务人员能完成一次预报、查看状态、回查 `run_id` |
| M5：高寒区验证 | 融雪与冻土模块参数、历史场次比较、诊断图 | 能说明高寒区过程启用前后的差异与适用范围 |
| M6：试运行 | 定时预报、备份、故障处理、操作手册 | 连续试运行期间无结果覆盖，抽样运行可复现 |

### 8.2 一期验收指标

| 类别 | 验收要求 |
|---|---|
| 可复算 | 任意一个已发布 `run_id` 可定位输入产品、参数、状态、代码版本、结果和日志 |
| 状态连续性 | 连续两次预报的状态时间无断裂；资料订正触发新状态链而不覆盖旧链 |
| 数据质量 | 每个入模产品有版本、校验码和 QC 摘要；缺测和替代资料可见 |
| 模型正确性 | 水量平衡、单位、时间步长、状态范围和断面序列长度自动检查 |
| 前端一致性 | 同一 `run_id` 下地图、表格、过程线和指标引用同一数据版本 |
| 运维性 | API、Worker、数据库和文件库的故障可定位；备份恢复演练成功 |

### 8.3 开工前必须确定的六项事实

这些不是技术团队可以凭空替用户决定的参数，必须在 M0 前明确并写入配置与文档。

1. 业务时间步长：小时、三小时还是日尺度；它决定数据聚合、状态保存和预报时效。
2. 预报降水来源：数值预报、雷达临近预报、情景雨量还是人工方案；它决定未来 forcing 的数据产品。
3. 试点断面与可用历史洪水场次：这是率定、验证和预报验收的共同基准。
4. 高寒区过程的一期边界：只做雨雪相态、度日融雪和冻土经验修正，还是已有可验证的更复杂模块。
5. 站网资料到达方式与订正规则：文件、数据库、HTTP、串口或人工导入；原始值和采用值如何区分。
6. 部署目标：本地单机、办公室局域网服务器还是后期云主机；它决定身份认证、备份和网络配置的力度。

## 九、第一批开发任务

1. 建立 Git 仓库结构、Python 虚拟环境、Vue 3 工程和 Docker Compose 骨架。
2. 用 Alembic 创建 `ref`、`obs`、`catalog`、`model`、`ops` 五类最小表，并导入一个流域的空间对象。
3. 冻结站点、子流域、河段、断面、变量和单位字典，禁止在脚本中自由拼写编码。
4. 导入一个已知历史洪水场次的原始观测，形成可审计的 QC 与采用值记录。
5. 生成第一个 `forcing.nc`，登记其变量、时间范围、校验码和上游来源。
6. 把现有新安江计算整理为纯 Python 模型核心，并为输入输出、状态范围和水量平衡写单元测试。
7. 实现状态快照、历史回算和一次正式预报的 `run_id` 档案。
8. 实现 FastAPI 的运行创建、运行查询、过程线查询和 SSE 进度接口。
9. 实现二维预报作业台的最小闭环：地图选断面、创建运行、查看过程线、进入档案。
10. 配置定时任务、备份、恢复演练和试运行日志，之后再扩展率定、复杂诊断和更多高寒区过程。

## 十、结论

你的“PostgreSQL + NetCDF 协同”判断应作为平台的基础原则保留，而且应比界面技术更早落地。PostgreSQL/PostGIS 管对象、空间关系、观测采用值、版本、运行档案和索引；NetCDF 管 forcing、状态和结果矩阵；Python 管预处理、模型和运行编排；Vue 作业台只消费稳定 API。

三峡项目可以教会本项目如何把站点、地图、过程线、预警和运行进度组织成可用的作业台，但不能决定你的数据真相、状态继承或可复算机制。第一期先做一个流域、一条完整运行链和一个二维作业台，后续无论增加高寒区过程、更多流域还是更复杂的展示，都有稳定的技术底座可依托。
